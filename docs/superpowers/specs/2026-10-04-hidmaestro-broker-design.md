# TASK 8L-C4L2 — HIDMaestro privileged broker design

## Purpose and acceptance boundary

Keep the interactive `ChatpadBridge.exe` process at normal-user integrity while retaining the existing HIDMaestro virtual Xbox backend. Move only privileged virtual-controller lifecycle and state submission into a Windows service. The user process remains the sole owner of physical WinUSB, Chatpad activation/keepalives and parsing, keyboard injection, physical controller state, and physical rumble output.

This task has two gates. The implementation and package must first pass offline verification. Installing, repairing, starting, stopping, or uninstalling the service on the live machine requires the user's separate elevated setup step. Normal-user hardware qualification follows only after that step and must independently prove physical WinUSB → bridge → service → XInput and virtual rumble → service callback → bridge → physical controller. This design does not authorize driver binding changes, driver installation, trust changes, reboot, or architecture/backend substitution.

## Chosen architecture

`ChatpadVirtualXbox.exe` gains a Windows Service mode and continues to contain the pinned HIDMaestro SDK adapter. The Service Control Manager launches that executable from the protected installed application directory as `LocalSystem`; it is configured for automatic start and bounded SCM recovery after an unexpected process failure. The existing `helper` process mode is removed from the production bridge path. `ChatpadBridge.exe` remains a normal-user process and connects to the installed service using one local, duplex named-pipe session.

The service exclusively owns `HMContext`, `HMController`, profile loading, device metadata checks/cleanup, virtual-controller state submission, SDK output subscription, and virtual controller destruction. The client continues to own USB device discovery, WinUSB handles and transfers, Chatpad state, keyboard injection, controller parsing, and the physical rumble callback destination. No physical USB handle or raw USB operation crosses IPC.

## IPC contract and authorization

Use a versioned local pipe name under `\\.\pipe\ChatpadHidMaestroBroker.v1`. The server rejects remote clients, permits only one active controller-owning connection, uses bounded newline-delimited UTF-8 JSON frames no larger than 4096 bytes, and serializes writes so responses and callbacks cannot interleave. The pipe DACL grants access only to `SYSTEM` and interactive logon tokens. For each connection the service impersonates the client and validates a non-anonymous local interactive token and session identity before processing requests. The authenticated logon SID and session ID own the active lease; another identity cannot take over an existing lease. The service reverts impersonation before all HIDMaestro/SCM work.

Requests and responses carry protocol `version: 1` and a nonnegative 32-bit correlation ID; the request parser uses exact property allowlists. Only these operations exist:

| Operation | Fields | Behavior |
| --- | --- | --- |
| `ping` | `version`, `id`, `op` | Return service/protocol readiness without constructing `HMContext` or creating a device. |
| `create` | `version`, `id`, `op` | Create exactly one pinned `xbox-360-wired` virtual controller for this connection after the existing metadata and present-device guards pass. Repeated create is rejected. |
| `submit-state` | `version`, `id`, `op`, `buttons`, `leftTrigger`, `rightTrigger`, `lx`, `ly`, `rx`, `ry` | Validate exact integer types/ranges and submit the existing `XboxState` conversion. Requires an active controller owned by this connection. |
| `destroy` | `version`, `id`, `op` | Submit neutral virtual state, detach output callbacks, dispose the controller/context, and release only metadata created by this service session. Physical motor stop remains the bridge's responsibility. It is idempotent when no controller is active. |

The service may send only a correlated response or a `rumble` event containing `version: 1` and bounded 16-bit `leftMotor` and `rightMotor` values. The bridge maps this event to the existing physical USB rumble write. Unknown operations/properties, duplicate JSON properties, malformed or oversized frames, out-of-range values, unowned state/destroy requests, stale IDs, and protocol-version mismatch fail closed and terminate the connection where framing/authentication is ambiguous. The service exposes no command shell, paths, arbitrary HID requests, process launch, driver installation, registry mutation API, or caller-selected profile.

## Lifecycle, reconnect, and failure handling

Each accepted pipe connection is one ownership lease. The bridge can create, destroy, and create again over that same authenticated connection, allowing the existing physical reconnect loop to retain its policy. On explicit destroy, the service neutralizes then disposes the controller before acknowledging completion. On client disconnect, process crash, malformed ownership traffic, or service stop, the service best-effort submits neutral virtual state, detaches output callbacks, disposes the controller/context, and releases session-owned metadata before clearing the lease. The service never writes physical USB or claims to stop physical motors. No second client is admitted until teardown completes.

If the service process terminates unexpectedly, do not assume Windows removed its software-device nodes. SCM recovery starts a fresh service instance with no active in-memory lease; it never adopts stale client state. On the next `create`, retain the current present-index conflict guard before the pinned SDK's normal create path. Do not call `InstallDriver`, the global `RemoveAllVirtualControllers` sweep, or any alternate cleanup API. If the existing guard or pinned create path cannot establish one unambiguous virtual device, fail closed and report the orphan rather than remove unrelated devices. The bridge treats pipe loss as a virtual-backend failure, closes the client session, cleans physical keys and motors using its existing shutdown path, and does not claim XInput readiness. Physical device loss/reconnect remains controlled by the existing runner and must recreate the virtual controller only after its existing readiness gates. On a live bridge disconnect while the process remains available, its existing failure path releases held keyboard state and sends zero physical rumble. On a bridge process crash, the service can only clean virtual-device state; it cannot write the physical USB device. The existing next-launch recovery releases abandoned keyboard keys and sends an initial zero-rumble command. Graceful client shutdown, pipe loss, forced client-process termination, service crash/restart, and subsequent bridge restart are separate offline and live acceptance cases.

All RPCs have bounded deadlines. State submissions remain at the existing one-second request limit; create and destroy use bounded 30-second limits. A timed-out or desynchronized session is poisoned and closed rather than reused. Cleanup results distinguish virtual neutral submission, controller disposal, metadata cleanup, physical cleanup performed only by the bridge, and pipe closure; failure is surfaced and never logged as clean shutdown.

## Setup and package behavior

Add explicit elevated `ChatpadSetup.ps1` modes `InstallBroker`, `RepairBroker`, and `UninstallBroker`; `Status` reports broker service name, state, start type, installed binary identity, and whether the caller is elevated. These modes operate only on the named broker service and protected `Program Files\ChatpadBridge` files. Install validates package/readiness identity and hashes, copies the exact service/runtime members into `Program Files\ChatpadBridge` and independently verifies their hashes, installs the service as `LocalSystem` with automatic start and documented recovery actions, starts it, and verifies its service identity/state. Repair requires the bridge stopped, stops the service and drains its lease, verifies/replaces only its exact installed files, reapplies the fixed SCM configuration, and verifies startup. Uninstall requires the bridge stopped, asks the service to stop and verifies virtual cleanup, deletes only the named SCM service registration, and retains shared HIDMaestro driver packages and the bridge files. Existing C4 physical WinUSB install/restore modes keep their current semantics; service lifecycle modes never change device binding.

Package/readiness manifests include the service executable and all runtime/configuration members using hashes computed from the exact packaged bytes. Installed service identity checks compare the resolved protected binary path and recorded member hash before start/repair. Missing, stale, modified, or ambiguous service metadata fails clearly; it is never accepted by skipping a member check. Generated package/build/evidence files stay under ignored `artifacts/`.

## Verification and acceptance

Offline verification covers strict request schema and ranges, correlation, unknown/duplicate fields, oversized/malformed messages, unauthorized token/session and second-owner rejection, ping without SDK/context construction, exact create/submit/destroy behavior, idempotent destroy, neutral/dispose on EOF and exception, rumble event framing, reconnect on a persistent lease, client timeout/session poisoning, service configuration and identity/hash regressions, and unchanged physical setup behavior. The focused native runner lifecycle tests prove that pipe loss cleans keyboard/physical rumble state and returns a failed runtime result. Package verification checks exact file set, source/package branch+commit identity, and every package/readiness hash.

After offline PASS, the user performs the explicit elevated service setup. Live normal-user qualification then records: service installed/running under the intended service identity; `ChatpadBridge.exe` is not elevated; authenticated pipe accepts only the intended local user session; WinUSB and Chatpad remain functional; virtual XInput appears and reflects buttons/axes/triggers; XInput rumble reaches the physical controller and motor-stop is observed; physical unplug/reconnect recreates the virtual device without stale state; graceful stop neutralizes/releases it; forced bridge termination causes broker cleanup; forced service termination/restart has no orphaned XInput state and cannot inherit a former lease. Any untested item is reported `UNTESTED`, not inferred from offline mocks.

## Constraints and alternatives

- Keep pinned HIDMaestro as the virtual backend; do not reopen backend research or substitute another backend.
- Preserve the existing fail-closed present-index guard before SDK create. The pinned SDK documents `CreateController` as admin-only and exposes `RemoveAllVirtualControllers` as a system-wide cleanup; the service must not call that global cleanup API for broker recovery ([v1.10.1 HMContext.cs](https://raw.githubusercontent.com/hifihedgehog/HIDMaestro/v1.10.1/sdk/HIDMaestro.Core/HMContext.cs)).
- Never elevate `ChatpadBridge.exe` or delegate its physical USB/input responsibilities to the service.
- Do not weaken device/registry ACLs, create hidden scheduled tasks, expose arbitrary privileged operations, or mutate the physical device stack from broker IPC.
- Do not install or start the service during offline implementation. The user must perform the live elevated setup step.
- A separate broker executable would duplicate the SDK packaging and process identity surface; a general-purpose privileged host or arbitrary-operation RPC would exceed the minimum required authority. The in-process service mode is therefore selected.
