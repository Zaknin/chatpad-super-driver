# ChatpadWinUsbPoc — bounded user-mode experiment

C2 prepares a native x64 monitor and explicit bridge. It does not prove WinUSB, real keyboard output, rumble or virtual XInput on this host. C1 physical descriptors were reread via documented hub queries under xusb22 and parsed offline; this is not live WinUSB ownership.

Build the offline managed helper first with `tools/ChatpadVirtualXbox/Build.ps1`, then `tools/ChatpadWinUsbPoc/Build.ps1 -Configuration Release` (or Debug). Outputs stay in `artifacts/task-8lc2/`. CMake/VS2022/MSVC v143/SDK10.0.26100 are required. These user-mode targets deliberately use the existing portable-test convention of SpectreMitigation=false; no working driver build configuration changes. Old TOOLCHAIN Spectre-readiness statements were not reconfirmed by C2's current libraries; default CMake probes failed MSB8040 and those logs remain.

Commands: `enumerate`, `descriptors`, `monitor-controller`, `monitor-chatpad`, `activate-chatpad`, `monitor-all`; finite default15 seconds, `--seconds 1..120`; select ambiguous physical targets with exact `--instance`. `descriptors --json-only` is machine-readable; `--json-out <path>` saves JSON alongside human output. `descriptors --fixture <raw-configuration.bin>` is explicitly offline. The application GUID is `{B6A5D05E-7E18-4DF1-8E47-12F072DE2C36}`; only whole-device045E:028E qualifies. Enumerate fails exit3 while xusb22 owns the device.

Monitor commands never create virtual devices or call SendInput. `--activate` on Chatpad/all monitors observes valid controller readiness first, runs the exact six working requests with12ms post-delays, starts001F then alternating001E/001F, and sends001B once after the first complete five-byte packet. No retries, guessed payloads, USB reset or alternate-setting switch. Native WinUSB cannot prove USBD_STATUS_STALL_PID from generic Win3231; it logs the exact failure and stops. The portable runner preserves the existing narrow proven-STALL policy, tested through typed mocks; real ambiguous errors are not relabeled.

Each overlapped operation owns its buffer/event until completion or cancellation drains. Reads have200ms windows, controls/output1000ms, cancellation drain2000ms. Separate controller/Chatpad threads prevent one channel starving the other. Graceful exit joins readers, forces keyboard release, neutralizes/disconnects virtual output, writes zero motors, then closes USB. A driver that fails to complete cancellation leaves heap request storage retained; output cleanup runs before Close terminates the POC with exit70. Device loss, UIPI, OS termination/crash or refused key-up can still prevent successful physical cleanup and are logged limitations. Reconnect is explicit fresh enumeration/open/process lifetime after removal, with a new one-shot activation; no autonomous rebind/retry.

`bridge --allow-live-bridge --backend-helper <absolute.exe> --backend hidmaestro --seconds 45` is future live execution, never run in C2. It wires controller parser to the replaceable IVirtualXboxController/native managed-helper client, SDK callbacks to source-backed IF0/01 rumble, and existing layered mapper to separate SendInput scan-code output. The compiled C2 helper has mock/unavailable backends; real HIDMaestro source needs a verified external SDK and .NET10 build. SDK create may have service/resource and upstream deployment side effects; read the backend document before authorizing it. Normal startup never installs a package.

Portable protocol remains unmodified: src/protocol/ChatpadProtocol contains activation tables, strict policy, exact five-byte parser, default Base/Green/Orange maps and held-key latching. Driver ChatpadLiveRuntime.c supplies the known001F/001E/001B maintenance sequence. Physical controller layout/rumble/LED are independently expressed from pinned C1 protocol knowledge; no GPL implementation copied. Controller20-byte00 14 packets decode every button/trigger/stick and preserve Guide; the parser rejects reserved bit11 and other types/lengths. Rumble00 08 00 L R 00 00 00 uses high-byte motor quantization, LED01 03 pattern0..13; both physical effects remain UNTESTED.

Headset/accessory interface1, security interface3, player-slot/LED association, Guide-aware consumers, crash watchdog, elevated targets/UIPI, production latency and ordinary-boot signing/SecureBoot/HVCI qualification remain unresolved. USB power and security settings stay unchanged.

Exit0 means command/finite capture completed, not full C3 acceptance;3 no intended WinUSB device,4 open failure,5 readiness failure,6 activation failure,7 maintenance failure,8 USB failure,9 reader exception,10 silent channel,11 keyboard failure,12 backend failure,13 rumble cleanup failure,70 undrained kernel I/O. Save raw timestamps and decoded output; validate actual press/release and intended virtual identity independently.
