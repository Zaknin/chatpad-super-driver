# ChatpadWinUsbPoc — bounded user-mode experiment

C2 prepares a native x64 monitor and explicit bridge. It does not prove WinUSB, real keyboard output, rumble or virtual XInput on this host. C1 physical descriptors were reread via documented hub queries under xusb22 and parsed offline; this is not live WinUSB ownership.

Build the offline managed helper first with `tools/ChatpadVirtualXbox/Build.ps1`, then `tools/ChatpadWinUsbPoc/Build.ps1 -Configuration Release` (or Debug). Outputs default to `artifacts/task-8lc2/`; C2R1 uses `-OutputDirectory C:/Dev/chatpad-super-driver/artifacts/task-8lc2r1/native -VirtualHelperExecutable <absolute-helper.exe>`. Builds and CTest cap workers at2; `-SkipTests` allows the coordinator to run one final integrated regression after dependency builds. CMake/VS2022/MSVC v143/SDK10.0.26100 are required. These user-mode targets deliberately use the existing portable-test convention of SpectreMitigation=false; no working driver build configuration changes. Old TOOLCHAIN Spectre-readiness statements were not reconfirmed by C2's current libraries; default CMake probes failed MSB8040 and those logs remain.

Commands: `enumerate`, `descriptors`, `monitor-controller`, `monitor-chatpad`, `activate-chatpad`, `monitor-all`; finite default15 seconds, `--seconds 1..120`; select ambiguous physical targets with exact `--instance`. `descriptors --json-only` is machine-readable; `--json-out <path>` saves JSON alongside human output. `descriptors --fixture <raw-configuration.bin>` is explicitly offline. The application GUID is `{B6A5D05E-7E18-4DF1-8E47-12F072DE2C36}`; only whole-device045E:028E qualifies. Enumerate fails exit3 while xusb22 owns the device.

Monitor commands never create virtual devices or call SendInput. `--activate` on Chatpad/all monitors observes valid controller readiness first, runs the exact six working requests with12ms post-delays, starts001F then alternating001E/001F, and sends001B once after the first complete five-byte packet. No retries, guessed payloads, USB reset or alternate-setting switch. Native WinUSB cannot prove USBD_STATUS_STALL_PID from generic Win3231. C2R1 explicitly enables a native protocol-stage policy: steps0..2 (zero-length preambles) and3 (initial two-byte read probe) may continue only on Error31 with zero transferred bytes and no inbound data, logged as `PROBE_REJECTED`, with raw Error31 retained and provenStall=false. This narrower stage set comes from the existing `ChatpadLiveTransferPolicy.c` accepted-rejection boundary. Step4 writes the immutable09 00 and step5 reads exactly two bytes; both remain strict. Device loss, access denial, cancellation, timeout, other errors and partial transfers stop every stage. The portable/default runner preserves typed proven-STALL behavior and refuses ambiguous31. Initial001F, alternating001E/001F and first-five-byte001B commands remain strict zero-length successes. Offline tests prove policy only; physical activation remains UNTESTED. Successful strict stages, then real five-byte key packets, must supply progress evidence in C3.

Each overlapped operation owns its buffer/event until completion or cancellation drains. Reads have200ms windows, controls/output1000ms, cancellation drain2000ms. Separate controller/Chatpad threads prevent one channel starving the other. Graceful exit joins readers, forces keyboard release, neutralizes/disconnects virtual output, writes zero motors, then closes USB. A driver that fails to complete cancellation leaves heap request storage retained; output cleanup runs before Close terminates the POC with exit70. Device loss, UIPI, OS termination/crash or refused key-up can still prevent successful physical cleanup and are logged limitations. Reconnect is explicit fresh enumeration/open/process lifetime after removal, with a new one-shot activation; no autonomous rebind/retry.

`bridge --allow-live-bridge --backend-helper <absolute.exe> --backend hidmaestro --seconds 45` is future live execution, never run in C2. It wires controller parser to the replaceable IVirtualXboxController/native managed-helper client, SDK callbacks to source-backed IF0/01 rumble, and existing layered mapper to separate SendInput scan-code output. The compiled C2 helper has mock/unavailable backends; real HIDMaestro source needs a verified external SDK and .NET10 build. SDK create may have service/resource and upstream deployment side effects; read the backend document before authorizing it. Normal startup never installs a package.

C2R1 adds `c3-session --seconds 120 --instance <exact-id> --backend-helper <absolute.exe> --backend hidmaestro` for the future scripted C3 operator procedure. Do not run it during preparation. Redirect stdin/stdout; stdout is newline JSON schema1 and stderr contains human errors. Each stdin line must be at most128bytes and use ordered fields `{"id":1,"command":"activate"}`. IDs must increase strictly. Supported commands in order are `activate`, `create-virtual`, `enable-mapping`, `enable-rumble`, `enable-keyboard`, then `stop`; stop works at every stage. The child starts two physical monitors with disabled keyboard/output. It requires a valid controller report before activation; strict activation/initial keepalive, successful one-shot001B and a decoded valid five-byte packet before virtual creation. Mapping, physical rumble and SendInput require their later commands. Commands acknowledge their matching id and actual result. Separate `controller`, `activation-stage`, `activation`, `key-data`, `chatpad`, `virtual-created`, `rumble-callback`, `rumble-output`, `fatal` and `closed` events expose raw transfer/progress evidence; these are not operator physical acceptance. The caller must verify XInput identity and physical mapping/rumble/layers independently before advancing. One-shot activation and maintenance stay in the same process/open lifetime. No speculative reactivation occurs.

The session stops on EOF, malformed/duplicate/reordered/out-of-order commands, transfer failure or deadline. Controls cannot start after deadline/stop; their timeout is bounded by remaining lifetime. Cleanup joins readers, forces all held keys up, submits virtual neutral, drains/disconnects callbacks, writes zero motors if physical rumble was enabled, then cancels/closes transport. Require `closed.ok=true` and exit0 after explicit `stop`; timeout/EOF is failed acceptance even when cleanup succeeds. OS crash/device removal can prevent physical cleanup and require the independent restore plan. C2R1 compiled this session and tested pure transition/parser policy only; no hardware session or output was executed.

Portable protocol remains unmodified: src/protocol/ChatpadProtocol contains activation tables, strict policy, exact five-byte parser, default Base/Green/Orange maps and held-key latching. Driver ChatpadLiveRuntime.c supplies the known001F/001E/001B maintenance sequence. Physical controller layout/rumble/LED are independently expressed from pinned C1 protocol knowledge; no GPL implementation copied. Controller20-byte00 14 packets decode every button/trigger/stick and preserve Guide; the parser rejects reserved bit11 and other types/lengths. Rumble00 08 00 L R 00 00 00 uses high-byte motor quantization, LED01 03 pattern0..13; both physical effects remain UNTESTED.

Headset/accessory interface1, security interface3, player-slot/LED association, Guide-aware consumers, crash watchdog, elevated targets/UIPI, production latency and ordinary-boot signing/SecureBoot/HVCI qualification remain unresolved. USB power and security settings stay unchanged.
